# Developing LotGrade v0

[Main README](../README.md) · [Civil 3D exchange](CIVIL3D.md) · [Acceptance checklist](V0-ACCEPTANCE.md)

LotGrade uses React and TypeScript in a shared drawing workspace, with Electron for the macOS and Windows desktop application. Project serialization and DXF export operate on the same typed model used by the editor. The browser development view is useful for interface work; native file dialogs and desktop persistence must also be checked in Electron.

## Requirements and commands

Use Node.js **22.12 or newer within the supported Node.js release** and npm. CI currently selects Node.js 22. The lockfile is part of the project: use `npm ci` to reproduce a checked-in dependency set. Python 3.12 or a compatible newer Python is required only for the independent DXF test.

```sh
npm ci
npm run dev
```

Open the URL printed by the development server for browser development. Start the production desktop application with:

```sh
npm start
```

This builds the renderer and Electron entrypoints, then opens the desktop application. Native save/open/export dialogs are available there. Browser development uses local browser storage and file downloads instead.

Run the normal quality gate before considering a change complete:

```sh
npm run check
```

This checks TypeScript, runs the core/export regression tests, and builds the production application. It must run when changing drawing tools, project schema, units, persistence, or export code, because all can affect the exported result.

## Independent DXF verification

The second verification layer reads files generated by the current exporter with a different implementation, `ezdxf`:

```sh
python -m venv .venv
```

Activate the environment (`source .venv/bin/activate` on macOS, `.venv\Scripts\Activate.ps1` in Windows PowerShell), then run:

```sh
python -m pip install ezdxf==1.4.3
npm run test:interop
```

Set `PYTHON` if the test should use a particular interpreter. For example, on macOS `PYTHON=.venv/bin/python npm run test:interop`; in PowerShell set `$env:PYTHON = '.venv\Scripts\python.exe'` first. Test-generated files are temporary artifacts, not the regression specification.

The independent check should verify the writer's actual output geometry, elevations, layers, closed state, units, and reader audit result. A successful read is necessary but insufficient: all those properties must also agree with the fixture's expected values. It still does not replace a real Civil 3D import.

## Browser and desktop behavior

```sh
npx playwright install chromium
npm run test:e2e
```

Run these tests on a native macOS or Windows session. Browser tests exercise project management, drafting, save/open, and export interactions. Desktop tests exercise the production Electron main/preload/renderer connection. Preserve test traces/screenshots on failure and inspect the actual failure before updating expectations.

The drawing model must stay independent of canvas display transformations. Panning, zooming, grid density, selection highlighting, and label positioning must never shift exported coordinates or elevations. Do not export screen-space geometry or replace a project's coordinates with local render offsets.

## Cross-platform bundles

The application is packaged with `@electron/packager`. A package is a folder containing the native executable and its supporting files, rather than an installer:

```sh
npm run package -- --platform=darwin --arch=arm64
npm run package -- --platform=darwin --arch=x64
npm run package -- --platform=win32 --arch=x64
```

Expected output folders:

| Platform | Output | Executable |
| --- | --- | --- |
| macOS Apple Silicon | `release/LotGrade-darwin-arm64/` | `LotGrade.app` |
| macOS Intel | `release/LotGrade-darwin-x64/` | `LotGrade.app` |
| Windows x64 | `release/LotGrade-win32-x64/` | `LotGrade.exe` |

Distribute the entire output folder, not just the Windows `.exe`. For macOS distribution, archive the `.app` with a tool that preserves executable permissions and bundle structure. CI uses `ditto` for macOS and `Compress-Archive` for the Windows application folder before uploading a platform ZIP. Download and extract that inner ZIP; raw artifact storage does not preserve POSIX permissions. Locally built v0 packages are development artifacts unless signed/notarized through a configured release process.

Electron Packager documents the supported platform/architecture combinations and folder-based application output. Creating a Windows bundle on macOS establishes packaging, not successful Windows execution. Native CI exists to exercise each supported operating system. [Official Packager documentation](https://packages.electronjs.org/packager/v20.1.1/index.html)

## CI and the export invariant

The [quality workflow](../.github/workflows/quality.yml) runs on macOS Apple Silicon, macOS Intel, and Windows. In every job, typechecks/builds, core/export tests, independent DXF checks, and application tests must pass. The job packages the application and reruns its desktop test against that native executable before a bundle is uploaded. It runs on pull requests, pushes to `main`, and manual dispatch.

New drawing entity types must be added to all of the following together:

1. The project model and file validation/migration rules.
2. The editor's drawing and property behavior.
3. The DXF exporter, including defined coordinate/elevation/layer semantics.
4. Regression fixtures and the independent-reader expectations.
5. Save/reopen/export interaction tests where behavior changes.

Do not add a draftable entity that disappears during export. Reject an unsupported project version or invalid entity with an actionable error; do not silently filter it out. Test output expected values should come from the specification/fixture, not from reparsing the exporter's own helper functions.

Fixtures are a compatibility contract. Investigate a failure before changing one. An intentional contract revision needs a documented receiving impact and a real Civil 3D check if the change affects the DXF profile. The unit and independent-reader gates reduce regressions; they cannot prove every future change correct.

The workflow's required-check setting is a GitHub repository rule, separate from the checked-in YAML. If protected-branch rules are enabled, require all three `Verify …` jobs before merging changes to `main`.

## Architecture changes from the research brief

The initial research proposed a Windows-first C#/WPF product and a full terrain engine. The explicit v0 requirement to execute on macOS and Windows selects an Electron/TypeScript application for this first implementation. Version 0 is a drafting and project-management foundation with Civil 3D linework exchange. It does not claim the future constrained terrain solver, automatic grading, LandXML TIN surfaces, engineering drainage analysis, or complete code compliance.

The existing research remains useful for later surface and grading work. When those features arrive, preserve this DXF route while adding independently tested surface exchange; never use a new surface workflow as a reason to remove linework export.
